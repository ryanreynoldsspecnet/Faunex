# Faunex Application Audit and Pilot Delivery Plan

Review date: 28 October 2026. Target: controlled first-tenant pilot by mid-November.

## Executive Assessment

Faunex has a useful platform administration foundation, a coherent .NET architecture, and a working production deployment path. It is not yet a complete auction marketplace. Several paths stop at read-only screens or draft records, and important account, compliance, and auction rules are not enforced correctly.

Keep the existing stack. A rewrite, separate frontend framework, or native mobile build would consume the delivery window without solving the launch blockers. Finish and test one complete tenant journey before broadening animal categories or marketplace modes.

The two-week target should be treated as a tightly scoped pilot, not delivery of the entire product brief. Online payments are required. The agreed payment model is tenant-owned merchant accounts receiving tenant sales directly, PayFast first, possible Yoco support later, and separate Faunex subscription billing once commercial terms are decided. An approved first-tenant live merchant account has not yet been confirmed.

## Findings Requiring Action Before Pilot

P1 means a pilot blocker for the affected feature. P2 means important hardening or a bounded limitation that needs a deliberate decision. Source references below refer to the unchanged audited master snapshot, `eb25ef855ceccb13df3b22fdff4b57d743cc0e05`.

### F01 P1 Disabled Accounts Can Still Authenticate and Existing Tokens Remain Valid

User administration stores inactive status as `LockoutEnd`, but login only calls `CheckPasswordAsync`. It never checks lockout, tenant activity, or current membership eligibility. JWT validation checks cryptography and lifetime but does not reload account state or validate a session/security version. Tokens last eight hours. Consequently disabling an account does not prevent a correct-password login, and deletion, role removal, tenant reassignment, or password reset does not invalidate an already-issued token before expiry.

Evidence: `Faunex.Api/Controllers/AuthController.cs:92`, `Faunex.Api/Controllers/Platform/PlatformUsersController.cs:138`, `Faunex.Api/Controllers/Tenant/TenantAdminController.cs:466`, `Faunex.Api/Program.cs:72`, `Faunex.Api/Auth/JwtTokenIssuer.cs:40`. Source-traced; no real accounts were disabled or modified during the audit.

Required: account/tenant eligibility checks at login and authenticated request boundaries; deliberate session revocation after security changes; failed-login throttling/lockout; tests for all of those transitions. The Blazor auth provider also needs expiry-aware state so the UI does not keep showing an expired login.

### F02 P1 Auction Integrity Is Not Sufficient for Real Trading

The canonical bid path accepts any positive amount on an active approved listing whose auction has `IsClosed == false`. It does not enforce starting price, an increase over the current highest bid, the declared minimum increment, start/end times, or a prohibition on bidding on one's own listing. There is no transactional arbitration against simultaneous bids or a bid racing auction closure.

An isolated execution accepted a bid of 1 against starting price 100 and an existing highest bid of 150, after `EndsAt`, from the listing's seller acting with Buyer permission. This verifies the service defect, not a production transaction.

Evidence: `Faunex.Application/Services/BidService.cs:12`, `:25`, `:71`, `:88`; `Faunex.Application/Services/AuctionService.cs:128` explicitly treats timestamps as informational. Closing an auction still has a TODO for selecting a winner at `AuctionService.cs:182`.

Required: a server-authoritative timed-auction state machine, validated schedules/prices, concurrency-safe bid acceptance and closure, reserve handling, deterministic winner/no-sale outcomes, and a persisted result that can create exactly one payable order. Test duplicate requests, equal bids, simultaneous bids, closure races, and seller self-bidding.

### F03 P1 Compliance Submission Can Bypass Document Requirements

Submission loads `Compliance` but not the animal detail navigations used to determine required documents. In a fresh DbContext those details are null, so the requirement function returns an empty set. The isolated check submitted a bird listing with zero documents and observed `UnderReview` rather than `PendingDocuments`.

Evidence: `Faunex.Application/Services/BirdListingService.cs:548`, `:591`, and `:415`. The older `SubmitForReviewAsync` path has the same loading issue at `:282`.

The canonical submission method only permits Draft, so a properly detected PendingDocuments state has no complete resubmission path there. The older duplicate submission method has different transition rules. Neither path implements the full tenant-specific document policy from the brief.

Required: one submission use case, explicit listing classification loading, configurable pilot document rules, verified upload records, resubmission after missing/rejected documents, and an append-only review history. Exact trading/permit rules must be supplied or approved by the business; this audit is not a legal compliance certification.

### F04 P1 Tenant Admin Listing Creation Is Blocked by Conflicting Permissions

The new Add Bird Listing screen is restricted to TenantAdmin and posts to `/api/seller/listings/bird`. That controller requires SellerOnly, and SellerOnly requires the Seller role. The first tenant admin is created with TenantAdmin only. The service accepts either role, but the controller rejects the normal first-admin request before the service executes.

Evidence: `Faunex.Web/Components/Pages/TenantListingCreateBird.razor:11`, `:186`; `Faunex.Api/Controllers/SellerListingsController.cs:11`; `Faunex.Api/Program.cs:95`; `Faunex.Api/Controllers/Platform/PlatformTenantsController.cs:102`.

The same policy mismatch affects auction create/open/close endpoints: controller policies require Seller, while open/close service rules require TenantAdmin. Define capabilities consistently and add HTTP-level tests with TenantAdmin-only, Seller-only, Buyer-only, platform, and anonymous identities. Do not solve this by giving every user every role.

### F05 P1 Custom Domains and Tenant Subdomains Are Only Partially Implemented

The application stores normalized, unique tenant hostnames and resolves active domains to active tenants. Public marketplace queries then explicitly scope approved content to that tenant. Those are useful building blocks.

However, the checked-in Caddyfile contains only `faunex.co.za`, `www.faunex.co.za`, and the old IP redirect. Domain creation only writes a database row; it does not provision DNS, routing, or certificates. There is no domain ownership verification state, reserved-platform-host protection, automatic default subdomain allocation, or end-to-end onboarding check.

Evidence: `deploy/Caddyfile:1`; `Faunex.Api/Controllers/Platform/PlatformTenantsController.cs:298`; `Faunex.Api/Tenancy/TenantDomainResolver.cs:8`. This is a repository finding; live VPS configuration beyond public HTTP responses was not inspected.

Required for pilot: prove one platform subdomain and one tenant-owned custom domain from DNS through TLS, branding, login, listings, and checkout. Use an explicit verified allowlist and manual operator provisioning initially if needed. Do not enable unrestricted on-demand certificate issuance. Caddy requires qualifying configured hostnames or a carefully controlled on-demand setup: [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https).

### F06 P1 Tenant Creation and First Admin Are Not Truly Atomic

The tenant is saved before the first administrator and role assignment. Known Identity failures trigger compensating deletions, but no shared database transaction spans the separate application and Identity DbContexts. An exception, disconnect, process restart, or failed cleanup can leave a tenant without its intended first administrator.

Evidence: `Faunex.Api/Controllers/Platform/PlatformTenantsController.cs:74`, `:94`, `:102`.

Required: a tested all-or-nothing transaction across both contexts, or a durable provisioning state that cannot activate an incomplete tenant. Test database exceptions as well as normal validation failures. Earlier descriptions of this flow as atomic were stronger than the implementation warrants.

### F07 P1 No Complete Listing to Sale Workflow

The tenant detail screen is read-only. There is no completed tenant-facing edit, document/image upload, submission/resubmission, and auction setup workflow. Seller screens exist but use older contracts and inconsistent navigation.

Selecting Auction in draft creation sets a null BuyNowPrice; it does not create an Auction. The isolated check confirmed an auction draft produces zero auction records. Creation also forces USD, quantity 1, and no location despite the South African use case. A fixed-price amount is not a functioning buy-now purchase workflow.

Evidence: `Faunex.Application/Services/BirdListingService.cs:134`, `:158`; `Faunex.Web/Components/Pages/TenantListingDetails.razor:306` only loads detail. Listing images have no complete managed upload/storage implementation in the reviewed source.

Required: complete the pilot bird-listing path with ZAR, species, necessary animal identifiers/details, location/quantity, images, protected compliance files, edit ownership rules, status visibility, and actionable next steps. Choose timed auctions as the first complete selling mode; hide unsupported modes rather than advertising partial behavior.

### F08 P1 Public Auction Contracts Do Not Preserve Sealed Bid Confidentiality

The anonymous marketplace bid-history endpoint returns bidder IDs and amounts, and current price returns the highest bid without checking sealed-bid status. Public auction DTOs also include ReservePrice. The browser auction screen displays the returned history. A hidden-bid/reserve policy cannot be preserved by hiding labels in the UI alone.

Evidence: `Faunex.Api/Controllers/MarketplaceController.cs:118`, `:158`, `:327`; `Faunex.Application/Services/BidService.cs:162`. Source-traced; no production sealed-bid records were accessed.

Required: public-specific DTOs and auction-type visibility rules. Defer and disable sealed bids for the pilot unless a separate confidential workflow is implemented and tested. Decide explicitly whether reserve prices are public or confidential.

### F09 P1 Current Dependency Advisories Will Reblock the Deployment Gate

The last successful workflow does not mean the dependency graph is still clear today. A fresh `dotnet list Faunex.slnx package --include-transitive --vulnerable` reports:

| Dependency | Observed version | Scanner severity | Location |
| --- | --- | --- | --- |
| System.Security.Cryptography.Pkcs | 9.0.0 and 10.0.8 | High and Moderate | API and Infrastructure/test dependency graphs |
| System.Security.Cryptography.Xml | 10.0.8 | High | Infrastructure and tests |
| MessagePack | 3.1.8 | Moderate | Aspire AppHost |

The checked-in workflow explicitly exits 1 when that output contains vulnerable packages, so a new run using the same advisory data is expected to block deployment. This was reproduced locally, not by triggering a new production workflow. Advisory presence does not by itself prove reachable exploitation in Faunex.

Evidence: `Faunex.Infrastructure/Faunex.Infrastructure.csproj:23`; `Faunex.AppHost/Faunex.AppHost.csproj:16`; `.github/workflows/deploy.yml:32`. Selected scanner advisories: [Pkcs](https://github.com/advisories/GHSA-846f-f764-76mx), [MessagePack](https://github.com/advisories/GHSA-qhrr-8q5h-9q3h), [Xml](https://github.com/advisories/GHSA-cvvh-rhrc-wg4q).

Required: review/remove unused packages or update supported compatible versions; rerun restore, advisory scan, Release build, tests, publish, and actual Actions checks. Keep the security gate. Add ongoing dependency updates/scans so this is routine maintenance rather than a launch surprise.

### F10 P1 Online Payments Need an Entire Vertical Slice

There are no implemented order, payment attempt, provider callback, reconciliation, or refund workflows in the reviewed code. Online payments are a confirmed pilot requirement, not a later optional feature.

Confirmed model: tenant sales use that tenant's own merchant account and settle directly to the tenant. PayFast is first. Yoco is a later provider option. Faunex's own tenant subscription/debit billing is a different money flow, with commercial terms still undecided; it must not be mixed with tenant auction proceeds.

Required pilot implementation:

1. A tenant-scoped payment-provider configuration with encrypted secrets, controlled admin access, safe credential replacement, test/live separation, and no secrets in responses or logs.
2. An order created from the authoritative auction result, with immutable tenant, buyer, amount, ZAR currency, and merchant-account association. Specify buyer fees, VAT, shipping, and payment due time before coding totals.
3. Server-created PayFast checkout using the correct tenant merchant credentials. The browser must not choose tenant, merchant, payable amount, or paid status.
4. An externally reachable HTTPS notification endpoint. Current Caddy routes all traffic to the web app and does not expose API callbacks; add a deliberately scoped route or web receiver rather than opening the entire API accidentally.
5. Provider-required signature, source/data, amount, currency, merchant, and order verification. Correlate the callback to the stored payment attempt; do not select a merchant solely from untrusted callback fields.
6. Idempotent callbacks and checkout retries, durable transaction references, recovery from delayed or reordered events, and a reconciliation view for paid/failed/cancelled/pending transactions.
7. A failed-payment/unpaid-winner policy, receipt/confirmation, and a documented refund/cancellation process. A pilot may use provider-dashboard refunds only if the business accepts and can reconcile that procedure.
8. Sandbox tests followed by an authorized low-value live payment to the first tenant account. Confirm actual receipt in the intended merchant account before launch.

A return/success page is not payment proof. Provider guidance: [PayFast notification checks](https://support.payfast.help/portal/en/kb/articles/what-causes-the-itn-security-check-errors-20-9-2022); [Yoco server-side checkout and webhook confirmation](https://developer.yoco.com/guides/online-payments/accepting-a-payment). PayFast integration details must be checked against its current documentation when implementing; no provider has been integrated or merchant credentials requested in this audit.

### F11 P1 Permission Hierarchy and Session Context Need Tightening

All platform user mutation endpoints use PlatformAdminOnly. Validation allows assigning PlatformSuperAdmin, so a normal PlatformAdmin can assign that higher role, including to themselves. The declared PlatformSuperAdminOnly policy is not used to protect those mutations. If the roles are meant to have different powers, the hierarchy is not enforced.

Evidence: `Faunex.Api/Controllers/Platform/PlatformUsersController.cs:14`, `:126`, `:207`; `Faunex.Api/Program.cs:108`.

Usernames/emails are globally keyed and each account has a single TenantId. Login looks up email globally without tenant-host context. This is not the eventual multi-tenant membership model from the brief. A tenant buyer cannot simply create a second independent account with the same email in another tenant. Registration also accepts a caller-supplied RegistrationHost and allows a tenantless Buyer if resolution fails; the platform registration restriction is in the web UI, not this API contract.

Required: agree a pilot identity contract. Prefer one identity with explicit tenant memberships if cross-tenant users are needed; otherwise document and enforce the temporary single-tenant restriction. Bind tenant operations to a validated host/membership context, reject unknown/inactive registration hosts, protect super-admin assignment, and prevent removing the last necessary administrator. Do not label this a proven cross-tenant data breach: the reviewed protected queries generally use tenant claims or explicit tenant predicates, but broad HTTP-level negative tests are still missing.

## Pilot Scope Recommendation

The pilot must demonstrate a complete bird-auction transaction for the first tenant while preserving tenant isolation. It must include a real custom domain/subdomain, secure accounts, tenant-owned PayFast checkout, and traceable sale/payment results.

Recommended deferrals: Yoco implementation, native apps, wallets, platform-managed seller payouts, subscriptions/automatic tenant debits, sealed bids, all-animal production workflows, advanced commission models, WhatsApp/push/SMS, advanced full-text search, and multi-instance scale-out. Leave clean extension points where justified; do not build speculative provider/billing frameworks before the first payment works.

Faunex subscription billing should later use its own merchant identity and billing records, separate from tenant orders and merchant credentials. Pricing, payment instrument, billing frequency, cancellation, and authorization/mandate rules still need a business decision. This audit does not assume subscription billing is required for the controlled pilot.
