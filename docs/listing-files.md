# Listing File Operations

## Scope And Access

Section 4B adds files to tenant/seller listing workspaces. Open **Files** from a listing, select Photo or Document, and upload one file at a time. Deletion requires confirmation. Only the owning seller or tenant administrator may modify files; platform super-admin/compliance reviewers may read evidence but not modify it. General platform staff and buyers cannot read private files.

Bytes are never served directly from a public directory. The API rechecks tenant, ownership and stored SHA-256 for each private download. PDFs download as attachments with a sandbox policy; they are never embedded as active browser documents. Only photo-category files on active, approved listings can be served anonymously, and only through that listing's verified tenant host. Responses use `no-store`; an already downloaded copy cannot be revoked from a recipient's device.

Changing files uses the listing revision token and returns an approved listing to inactive Draft. Review, suspension and existing auction activity lock file changes. Concurrent auction creation is still Section 5 work. Full evidence review UI/history follows in 4C.

Documents are optional by default. Configured tenant/animal-class requirements accept only linked, intact managed evidence, not legacy external URLs. Old metadata remains in the database, but arbitrary external file links are no longer offered by the tenant detail page. This does not remove copies that may already exist on an external service. Requirement-management UI is deferred pending business decisions; do not edit live policy tables casually.

## Formats And Limits

- Photos: JPEG/PNG, up to 5 MiB input. Document uploads also accept PDF up to 10 MiB.
- Images: maximum dimension 8,192; maximum 16 million decoded pixels; no animation. Match extension, MIME and decoded format. Fully decode and re-encode, correct EXIF orientation, resize to longest edge 1,800, strip metadata, cap stored image at 4 MiB.
- PDF checks cover name/MIME/header/trailer and antivirus verdict, not complete PDF structural or legal validation. Encrypted/over-limit scanner results fail closed.
- At most 10 photos / 30 active files per listing and 1 GiB of active file bytes per tenant. Limits are code constants, not subscription billing entitlements.
- Two concurrent image decoders and four concurrent API upload/thumbnail requests; excess work receives 429. Private previews are at most 320 pixels / 150 KiB.
- All original input is scanned before persistence. Stored images are normalized copies, not original forensic records. Both original and stored hashes are retained; original image bytes are not retained. PDFs retain their uploaded bytes.

## Deployment And Scanner

Docker Compose creates `listing_files` and `clamav_data` named volumes. Their actual names normally include the Compose project prefix. The API mounts file storage at `/var/lib/faunex/listing-files`; only the API mounts this volume. Keep it outside `wwwroot`. Keys are generated by the server, never taken from uploaded names. Stored Linux files have mode 0600.

The user confirmed a dedicated 4 CPU / 8 GB VPS. ClamAV uses a maximum 4 GiB RAM and 1.5 CPUs, two scan threads, and `ConcurrentDatabaseReload no` to reduce reload memory peaks. It listens only inside the Docker network; do not publish port 3310 or add a VPS ingress rule for it. Definitions persist across replacement containers and FreshClam updates them. `FailIfCvdOlderThan 7` refuses stale definitions. There is no bypass-to-clean fallback.

The first image pull/database initialization can take several minutes. API/site startup does not wait for scanner health: uploads return 503 until a complete clean verdict can be obtained. During a definition reload, uploads can briefly be unavailable. A clean antivirus verdict reduces risk; it does not guarantee that any document is harmless.

Read-only deployment checks in `/home/ubuntu/faunex`:

```bash
docker compose ps -a
docker compose logs clamav --since 10m --tail 100
docker compose exec -T clamav clamdscan --config-file=/etc/clamav/clamd.conf --ping=1
docker stats --no-stream
df -h
docker compose logs faunex-api --since 10m --tail 100
```

No new SMTP/JWT secrets are needed for uploads. `Files__ScannerHost=clamav` and `Files__RootPath` are set by Compose. A local development API without a configured scanner deliberately refuses uploads. CI uses the same scanner image/config, native Linux image library and isolated PostgreSQL databases. Test-only in-memory storage/scanner doubles must never be registered in production.

## Backup And Recovery

Back up PostgreSQL, `listing_files`, and existing data-protection keys as a consistent set, off the VPS with restricted access. File bytes without database records, or a database dump without file bytes, do not constitute a restorable upload store. Existing Caddy certificate volumes remain operational data too. `clamav_data` can be re-created but causes a cold-start update delay. Never use `docker compose down -v` or volume prune as deployment housekeeping.

Before rollout, check free disk, existing backup coverage and memory pressure. There is no automatic storage-backup scheduler or verified restore drill in this section. Define retention with the owners before real personal documents are collected. Soft-deleted metadata/hashes are retained; deleted bytes are removed after the database commit. A crash or disk failure can leave an orphan. Cleanup failures log a storage key and require reconciliation against active `ListingFiles` rows; do not delete a volume to fix one object. No automatic orphan collector is claimed.

File integrity failures/missing bytes fail closed with 503. Restore the matching known-good object and investigate rather than changing hashes to accept unexpected content. Never paste uploaded documents, credentials or raw private download responses into logs or issue reports. Application events log actor/tenant/listing/file identifiers, not file contents.

## Acceptance After Approved Merge

Use disposable test listings/accounts, not real permits or customer records:

1. Verify the exact master validate/deploy jobs are green and scanner health/resources are stable.
2. On Stormbird, create a draft and upload a normal JPEG/PNG and optional PDF. Reload; verify photo preview, private download, and confirmed deletion.
3. A different seller, buyer or tenant must not read that private evidence. A draft photo must not have a public URL that works.
4. Using the authorized review workflow, approve a listing. Its photos should load on Stormbird only; PDF evidence remains private. Change a file and confirm the listing becomes inactive Draft and public photo reads stop.
5. Recreate/restart the API container without removing volumes. Verify a retained file still downloads and its database linkage remains intact.
6. Perform a separate isolated scanner outage check and off-server backup/restore drill before closing pilot operational acceptance. Do not stop the live scanner or introduce antivirus test files on the VPS without explicit authorization.

Do not mark these production checks complete from local tests. Section 4C still needs reviewer inspection/history and a demonstrated complete submission/decision/resubmission journey.
